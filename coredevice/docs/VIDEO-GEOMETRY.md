# 视频几何与帧完整性

## 内容矩形

HEVC 编码尺寸可能包含对齐 padding，不能直接当作屏幕尺寸。App 在协商中声明内容矩形能力，优先使用通过校验的视频元数据，缺失时使用与显示目标绑定的 DeviceInfoService 元数据。矩形须有限、正数、整像素、位于 SPS 范围内且方向一致；歧义或过期信息不可用于裁剪。

已观察的私有 VCL 尾部包含 BE16 内容矩形及标记；部分 profile 还包含编码尺寸。解析先去除整个 NAL 的 emulation prevention，验证支持的布局及 SPS 约束，只移除已确认元数据，再重新转义 slice。转义可跨 slice/footer 边界，不能固定截掉若干 EBSP 字节。未知布局原样保留。

帧与几何按同一快照绑定，Core Image 坐标原点转换后裁剪，不缩放、不按像素颜色去边、不合成边缘。独立接收与解码对比发现，个别视频的最右暗列来自已编码画面；单独截图服务没有同样边缘。确切内部原因尚未证实，裁剪元数据不能恢复源端缺失像素。

## 静态画面与新鲜度

静态屏幕可以停止产生新视频帧，同时继续发送 sender report。PLI 请求编码恢复，不保证采集源立即提供新图片；重复请求不能当作同步截图接口。

截图满足以下任一条件才完成：

1. 请求后到达的完整图片已解码。
2. 请求后新的 sender report 确认已发包全部接收，组帧器同步且无未完成/重排帧，解码器在同一 stream epoch 到达该确认序号。

第二种情况确认画面保持不变，并非超时后返回任意缓存。新包、丢包、重复掩盖缺口、解码落后或 epoch 重置均撤销旧确认。无报告或死流仍超时。组帧/解码故障才请求恢复关键帧，不为每次静态截图持续发送刷新。

## 带宽与验证结论

源端缓冲耗尽曾导致 RTP 序号缺口，即使 sender/receiver 的成功传输计数相等也不能排除缺包。单变量验证确认 RCTL 中带宽字段的含义；ESP32 NCM profile 在协商和反馈中使用 2000 kbps，消除被测链路的初始突发与丢包。这个预算适用于当前转发能力，不是所有 iOS 传输的通用上限。

受控实机比较验证了 padding 裁剪、静态画面确认以及后台切换目标 App 后的画面更新。它不证明无限后台运行、所有旋转组合或所有设备兼容。仅关闭本地传输曾留下远端媒体，因此正常释放使用协商标识定向停止并核对会话；异常关闭仍不代表远端确认，也不调用全局 stopAll。
